# Fidelity

"Will my document survive?" is the first question anyone asks a Word alternative. Docxtor answers it with numbers.

## Three kinds of fidelity

| Kind | Question | How Docxtor measures it | Status |
|---|---|---|---|
| **Preservation** | If I open and save without editing, is my file unchanged? | Part-by-part comparison of the original and the re-saved package. | Automated: `docxtor corpus` |
| **Model fidelity** | If every paragraph were touched, what would the model lose? | Same comparison after forcing the whole body to be re-serialized from Docxtor's model. | Automated: `docxtor corpus` |
| **Visual fidelity** | Does it *look* like it does in Word? | Would need each page rendered with a reference renderer and with Docxtor, and the images compared. | Not measured |

### Scoring

`fidelity::compare` walks every part of the original package:

- byte-identical parts score 1;
- XML parts that differ are parsed and compared as multisets of element signatures (name + attributes, ignoring revision-tracking noise such as `w:rsid*` and `w14:paraId`) and text nodes — the Jaccard similarity is the part's score;
- missing parts score 0.

The main document part carries half of the total weight. The result is a percentage.

### Running it

*Sketch, not run by a test: it builds the release program and scores a folder of your own files.*

```bash
cargo build --release -p docxtor-cli
./target/release/docxtor corpus path/to/docs            # table
./target/release/docxtor corpus path/to/docs --json     # machine-readable
./target/release/docxtor corpus path/to/docs --min 99   # exit 1 if any file scores below 99% or fails to open
```

### Current results

On the fixtures in this repository (generated by python-docx and by Apple's `textutil`), every file opens, scores **100%** untouched and **100%** under forced re-serialization, and keeps its text exactly. This set is small and friendly. The wider checks below run on public files.

## Word compatibility: two programs, as gates

What Word accepts is checked by two programs, without a copy of Word. Both **fail the run** (exit 1) when Docxtor breaks a rule.

**1. Microsoft's Open XML SDK validator** (`tools/ooxml-validate`, run by `scripts/validate.mjs`, `npm run corpus:validate`). The rule: an error in a file Docxtor wrote fails the run unless (a) the original has the same error (same id, part and description, counted), or (b) `scripts/validate-allow.json` names it with a reason. A file Docxtor makes from nothing has no original, so every error in it counts. What it runs on:

- the 100-file sample of public files (`npm run corpus:fetch`): the original, Docxtor's forced re-write and Docxtor's save after a few edits, with the original's errors taken away;
- Docxtor's own files: the fixtures, `docxtor new` (blank and from Markdown);
- **the feature files**: one saved file per op kind (and one per recorded op shape), plus built documents (a table, a picture, a footnote, a list, a header and field, an equation, a chart, shapes, content controls, citations, an index, a table of contents, mail merge, and a document for each op kind that needs a set-up) and the other formats converted (`fixtures/formats`). They are made by `cargo test --profile gate -p docxtor-core --test random_ops feature_files` (the `gate` profile is `release` without link-time optimisation, so it builds faster; code in `crates/docxtor-core/tests/common/features.rs`, set-ups in `tests/data/feature_builds.json`, shapes from `tests/data/op_shapes.jsonl`). Every op kind is covered or named, with its reason, in `features::NOT_COVERED`; a test fails when a kind has neither.

**2. LibreOffice** (`scripts/lo-check.mjs`, `npm run corpus:lo`): a PDF of the original and a PDF of Docxtor's save, through the same converter and fonts. The rules, in the header of the script: Docxtor's save converts when the original does; the text is identical once whitespace is made one space; the page count is equal. A feature file has no original, so the file is its own: LibreOffice must convert it, it must make a page, a built document must show the text its entry lists, and Docxtor's re-save of it must read the same. Exceptions go in `scripts/lo-allow.json` (file, rule, reason).

Both allow-lists are empty: nothing Docxtor writes is excused.

Both run nightly (`.github/workflows/nightly.yml`: .NET 8, LibreOffice and poppler from apt, the pinned corpus cached on `scripts/corpus.mjs`). The quick part (feature files, one per op kind, and the fixtures through the validator) runs in CI (`word-quick` in `ci.yml`), in a few minutes. What they cannot say: whether Word draws a thing as intended (a gradient's angle, a label sheet's measures, the order Shift+F3 cycles the case in). Docxtor does not claim them.

## How to "guarantee x%"

No editor can promise a fidelity number for documents it hasn't seen. What Docxtor can do — and does — is:

1. **Never lose what it doesn't understand.** Unknown content is carried as opaque XML in its original position, so preservation fidelity is structurally 100% for untouched content.
2. **Score a public corpus** on every commit, and fail CI if the score drops.
3. **Grow the corpus** from real files contributors submit (scrubbed of private content).

### Where AI fits

AI doesn't change what the parser understands, so it doesn't raise preservation fidelity. It helps in the cases that remain:

- turning messy or converted documents (PDF-to-Word output, pasted web content) into clean, properly styled structure;
- explaining and repairing documents with layout problems;
- doing semantic edits that keep the author's existing styles instead of adding direct formatting.

## Visual fidelity

How Docxtor's page layout compares with Word's is not measured. Docxtor lays pages out with the browser, and it substitutes metric-compatible open fonts (Carlito for Calibri, Caladea for Cambria, Arimo for Arial, Tinos for Times New Roman, Cousine for Courier New, Gelasio for Georgia) so line breaks match Word when the original fonts aren't installed.

## Imported content chunks

Files from report generators, content systems and docx libraries often hold `w:altChunk` elements: HTML, a web page archive (MHT), plain text, RTF or a whole .docx stored as a part of its own, which Word turns into content when it opens the file. Docxtor shows them in place, in the body, in table cells and in content controls, converted with the readers the clipboard and the file opener use (styles, lists and pictures of a .docx chunk are carried as a paste carries them). Opening and saving without touching a chunk keeps the element and its part byte for byte. The first edit inside a chunk turns it into ordinary content, in the same undo step, and the next save leaves the chunk's part out. Chunks in headers, footers and notes still show as kept content. EMF pictures (object previews too) draw gradient fills; EMF+ records are skipped in favour of the plain EMF drawing every dual file carries.
