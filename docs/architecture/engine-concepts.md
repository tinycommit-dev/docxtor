# How the engine works

The ideas behind `docxtor-core` that the rest of the code relies on. Part of the [architecture](index.md) pages; the modules are in [files and the model](engine-files-and-model.md), [rendering and layout data](engine-rendering-and-layout.md), [content features](engine-content-features.md) and [AI tools and fidelity](engine-ai-and-fidelity.md).

## Positions

A position is `{p: paragraph id, o: offset}` where the offset counts UTF-16 code units in the paragraph's *flattened text*: text as-is, tabs as `\t`, line breaks as `\n`, inline objects (images, shapes, note references) and equations as U+FFFC, and zero-width markers (bookmarks, field codes) as nothing. UTF-16 matches what browsers report, so the UI never converts.

## Stories

Headers, footers and footnotes are loaded as stories that share the body's id space. An op is routed by the paragraph it targets: if that paragraph lives in a story, the story's blocks stand in for the body while the op runs, and new relationships (links, images) go into the story's own part. So every op — typing, formatting, tables, images — works in a header exactly as in the body, and the AI tools reach them the same way. Only edited story parts are rewritten on save; the rest stay byte-identical.

The text of a text box or shape is a story of kind `TextBox` (part = the part holding the shape), so typing in it is an ordinary op routed into the story. The shape's own element keeps its markup; after each op batch `Document::sync_text_boxes` writes the changed text back into the shape's `mc:Choice` and its `mc:Fallback` copy, and drops stories whose shape was deleted. An in-memory marker on the shape's element ties it to its stories and is never written.

## Undo

Each op batch snapshots the body, stories and styles/numbering before applying; typing coalesces into word-sized steps. The live body is shared with the steps, copy on write: `Document::body` is a `Body` (`crates/docxtor-core/src/body.rs`), a list of `Arc<Block>` for the top-level blocks (blocks inside tables, cells and containers stay plain). A snapshot (`Snapshot::body` is a list of `Arc<Block>`, itself shared with `PartCopies::blocks`) only counts references, so the first step after opening copies nothing; writing goes through `Body::get_mut`, `IndexMut` and the helpers (`parent_mut`, `try_edit`, `edit_each`, `edit_where`, `iter_mut_where`), which clone one block, and only when a step still shares it (`Arc::make_mut`). A whole-body pass finds the blocks it changes with a read first, so a step that touches one paragraph copies one block. `PartCopies::blocks` is the last snapshot's blocks: a block whose `Arc` is not the same as that one's is fresh in the step, which is what the memory budget counts (and what marks it as changed since the one before: `Changed::since_copy`, fed by every `touch`, `touch_all` and `changed.insert`, which is also what marks them for drawing). Undo and redo (`restore_body`) put the step's `Arc`s in as the body and mark for drawing the blocks that are not the live ones. Anything that changes a block without marking it, or copies it for writing without changing it, is caught in debug builds and tests, where each snapshot panics naming the op for a block that is not the last copy and was not marked. The history is held to 500 steps and a memory budget (128 MB), oldest first. A step counts the blocks it copied fresh, its stories, and the copy it owns of styles, numbering, settings and each story part (footnotes, headers, footers); a part a step leaves unchanged is shared with the step before (`PartCopies`), so it is held, and counted, once. `Document::pin(checkpoint)` makes the limits soft: no step from that checkpoint on is let go until `unpin` (the AI panel pins for a run and its review card, so "Changes" and "Revert all" always have what they need). A checkpoint that was let go anyway makes `diff_since` return nothing and `revert_to` do nothing.

## Change tracking for rendering

Ops record which top-level blocks they touch. `render_changed` renders only those (plus blocks whose list labels changed), so typing in a long document re-renders one paragraph.

The JSON a render sends: `blocks` (the ones drawn: all of them for `render_all`, the changed ones for `render_changed`), `full`, `stories`, and the block `order` (the visible top-level block ids). `render_changed` sends the order only when it moved (`Document::last_order` is the one the last render gave, compared as the blocks go by, nothing built when it is the same): then `order` is absent and `orderKept` is `true`, and the client keeps the list it has. Typing, formatting and undoing a keystroke keep it; a block added, removed or moved, or any undo or redo that changes the blocks, sends it again; `render_all` always sends it (an absent `order` without `orderKept` is an empty list, nothing visible). A client mirroring the engine (the editor, its other pane of a split window, a test) must keep the last list it was given and use it when `orderKept` is set; `Engine.renderAll()` in `@docxtor/core` always has it. The editor keeps the index of each block in the order as well, so a keystroke looks at the one block that changed and its two neighbours.

What the whole-document passes of a render read (the note references and section ends in each block, each list paragraph's list, level and style, whether a block holds a shape) is kept per top-level block in `document/facts.rs` (`Facts`, `ShapeFacts`). `Changed` has a set for each reader beside the one for drawing (`facts`, `shapes`, `since_copy`), fed by the same `insert`; a block is read again only when it is in the set, the order of the blocks is compared by id on every render (blocks that came, went or moved are found between the blocks that kept their place), and the results (note numbers and labels, list labels, section properties) are built again only when some block's facts differ. Styles, settings and section properties are not cached there: a change of the `RenderKey` makes the lists or notes count again, a change of the numbering part (`Numbering::gen`, which every change of the definitions moves) the lists. The cache is used only inside `render_changed` and `render_all`; everything else walks the document. In debug builds and tests every result built from the cache is compared with the walked one and panics on a difference (a block changed without `touch`, or a result depends on something not tracked). What an op does before and after a batch (`batch_watch`, `after_batch`) asks `body_has_shapes` before scanning for connectors and text boxes; locks and bookmarks are still read by walking.

## The input budget

`budget.rs` holds the one limit every reader of outside input spends from. `open::open` (and `Document::open`) make a `Budget` and hand it down the reader chain: the zip reader spends bytes inflated and parts, a `w:altChunk` that holds a .docx opens with the same budget one level deeper (and converts each part once), tabs and chunks spend their counts. When a limit runs out the open ends with one error, code `too-big`, "This file is too large or too deeply nested to open." `xml::parse` enforces depth for every format: `XML_DEPTH` for elements and `NEST_LIMIT` for weighted nesting of tables, content controls, text boxes and insertions; `tests/all/budget.rs` opens, draws, edits, saves and drops files at those limits on a 1 MB stack. Paste, picture and list readers check their input size against `budget::caps`, where the per-format caps (RTF, TIFF, .xlsx, ODT) live. A new reader takes a `Budget` or checks `caps`; it does not bring its own constants.
